# Svelte integration review — 2026-09-07

The `2-1` branch can build against the merged `main`, but its Svelte integration is not current or production-ready without further work. Passing existing tests does not establish SSR, IAB, or cross-framework parity. The maintainer has already addressed several of these gaps on the separate `v3` development branch.

## Findings

### P1 — Server hydration cannot read the cookie the client writes

Location: `packages/svelte/src/lib/server/index.ts:13-50,57-63`.

The server defaults to `c15t-consent` and parses JSON. The actual client persistence writes the `c15t` cookie using compact flattened keys, through `packages/core/src/libs/cookie/operations.ts` and `packages/core/src/store/initial-state.ts:19`. Changing only `cookieName` will not fix the format mismatch. The helper also does not restore `initialHasConsented` or the subject ID.

Reproduced by writing a cookie with the real core `setCookie('c15t', { consents, consentInfo })` function and passing `document.cookie` to `readInitialConsentConfig`. Expected the saved consents; received `undefined`.

Consequence: returning visitors lose their saved consent state during SSR. Client hydration can recover from browser storage, but server-rendered consent decisions cannot rely on this helper.

The inspected `v3` implementation uses `readStoredConsentFromCookie` from core and restores consent status and subject ID. Backport the shared parser and its integration tests together, rather than copying another parser.

### P1 — Server prefetch drops Global Privacy Control by default

Location: `packages/svelte/src/lib/server/index.ts:65-119`.

`readInitialConsentConfig` extracts country, region, and language but not GPC. `prefetchInitialConsent` forwards cookies and explicit `forwardHeaders` only. The separate `extractRelevantHeaders` helper handles `sec-gpc`, but this execution path never uses it.

Reproduced with an incoming `sec-gpc: 1` header and a mocked transport fetch. The outgoing request contained neither the header nor a GPC override. The documented basic SSR configuration therefore cannot convey that signal to backend policy resolution. Explicit `forwardHeaders: ['sec-gpc']` is a limited workaround.

The inspected `v3` server helper uses shared request-input normalization that includes GPC. Port the shared normalization contract with tests for the actual outgoing request.

### P1 — Hosted IAB cannot initialize from a backend-provided CMP ID

Location: `packages/svelte/src/lib/components/consent-manager-provider.svelte:485-497,528-533,564-572`.

IAB is created only during `onMount`, and `normalizeIabOptions` requires a numeric `options.iab.cmpId`. It does not use the backend-provided snapshot CMP ID or retry after asynchronous initialization. The bundled demo enables IAB without a local CMP ID. In that configuration, a later hosted IAB response cannot create the IAB handle, and the exposed mutation/save methods fall back to no-ops.

This finding comes from tracing provider control flow, not a live hosted-CMP browser test. The current `v3` provider/runtime has lazy IAB initialization and a regression test named `mounts hosted IAB after init supplies the CMP ID`.

### P2 — Unrelated option changes reinitialize consent

Location: `packages/svelte/src/lib/components/consent-manager-provider.svelte:65-66,583-607`.

The provider derives a fresh `options` object. Effects that read `options.user` or `options.overrides` track that object. Replacing an inline options object for a theme change reruns these effects, including `init()` and potentially `identify()`.

Reproduced by rendering with a counting custom transport and replacing only the theme: the initialization count changed from 1 to 2. The existing test claiming to cover theme changes does not rerender the component and runs offline, so it misses this.

Use stable derived values for the specific inputs and untrack incidental reads. This follows the current [Svelte effect dependency documentation](https://svelte.dev/docs/svelte/$effect#Understanding-dependencies) fetched through Context7. Upstream [#1068](https://github.com/c15t/c15t/pull/1068) also explicitly addresses this behavior.

### P2 — Prefetch does not produce a server-rendered banner

Location: `packages/svelte/src/lib/use-banner-visibility.svelte.ts:34-43`, `packages/svelte/src/lib/components/consent-banner.svelte:251`, and `packages/svelte/src/lib/components/iab-consent-banner.svelte:147`.

Both banners require `visibility.isMounted`. It starts false and becomes true only in `onMount`, so even resolved server prefetch cannot put the banner into the first HTML. The provider also calls `init()` on mount regardless of prefetch. This limits the SSR behavior described in the quickstart.

This is established by the render guards; a production browser hydration/visual parity run was not performed. Upstream [#1068](https://github.com/c15t/c15t/pull/1068), merged into `v3` on 2026-09-06, adds initial HTML banner rendering and a dedicated SSR test split.

### P2 — Conformance reports overstate coverage

Location: `packages/svelte/src/__tests__/conformance.test.ts:57-118` and `internals/conformance/src/suite/helpers.ts:41-55`.

The driver manipulates `getOrCreateConsentRuntime`, the old store, while the provider creates its own v3 kernel. Assertions made through that store are not observing the provider's real state. IAB mounting and server rendering throw `DriverNotImplementedError`; the shared wrapper catches that error, logs a todo, and returns successfully. Those checks count as passed rather than genuine parity coverage.

Connect the driver to the mounted provider's kernel, make unsupported cases explicit skips/failures, and separate client and SSR transforms. Do not interpret the 167 passing tests as verified SSR/IAB parity.

### P1 for publishing — This adapter depends on fork-only runtime exports

Location: `packages/svelte/src/lib/components/consent-manager-provider.svelte:1-30` and `packages/svelte/package.json`.

The adapter imports `c15t/v3`, its module subpaths, and `@c15t/iab/v3`. These are supplied by the early API-preview commit retained on `2-1`; the inspected stable `main` manifests do not export them. A successful workspace build does not mean this adapter can be published alone against unmodified stable c15t 2.2.1.

Ship a compatible dependency set from the fork or move to the newer runtime architecture. Test installed package tarballs in an isolated consumer before any release. The latest `v3` implementation imports `@c15t/core` and adds `@c15t/svelte/kit`, `/kit/locals`, and `/devtools`; those entry points are absent here.

## Recommended next implementation

Use this merged `2-1` as the preserved baseline. For a production integration, first decide whether the consumer must stay on stable 2.2.1 or can adopt the newer v3 runtime. For stable compatibility, backport the shared cookie/GPC fixes and the provider lifecycle corrections with real integration tests. For v3, assess the complete newer runtime and SvelteKit layer together; a Svelte-directory-only cherry-pick is insufficient. In both cases, finish with installed-tarball consumer tests and fresh SSR/hydration, returning-visitor, IAB, keyboard, and style checks.
